# Защита проекта перед экспертами

## Короткий питч (40–60 секунд)

«Smart Home PRO — единая локальная платформа управления домашними устройствами. Я сфокусировался не на статичном интерфейсе, а на работающем вертикальном срезе: команды проходят через API, состояние устройств хранится на сервере, события автоматически запускают сценарии, а изменения в реальном времени приходят в интерфейс. Важная особенность — local-first подход: базовые сценарии не зависят от облака. Для конкурсной демонстрации используется симулятор устройств, который позволяет воспроизводимо показать датчики, освещение, климат, розетки и охрану без закупки оборудования. Архитектура предусматривает подключение физических устройств через адаптеры протоколов».

## План демонстрации (4–5 минут)

1. **Обзор (30 сек):** показать онлайн-устройства, климат, охрану, энергопотребление.
2. **Управление (45 сек):** поменять яркость, температуру и розетку; объяснить путь UI → API → domain → persistence.
3. **Автоматизация (60 сек):** включить «Ночной свет», вызвать событие движения. Показать включившийся свет и запись в журнале.
4. **Безопасность (60 сек):** оставить охрану включённой, смоделировать открытие двери, показать тревогу и событие severity danger.
5. **Надёжность (30 сек):** показать, что состояние сохраняется после перезапуска сервера; открыть вторую вкладку и показать SSE-синхронизацию.
6. **Инженерная часть (45 сек):** `npm test`, архитектурную схему и список честных границ MVP.

## Что рассказать об инженерной ценности

- Не «кнопки меняют текст», а команды обрабатываются на сервере и валидируются доменной моделью.
- Правила автоматизации отделены от интерфейса и срабатывают на события датчиков.
- SSE даёт push-обновления состояния всем открытым клиентам.
- Local-first снижает зависимость от внешнего облака для локальных сценариев.
- Симулятор создаёт повторяемую среду для тестов и демонстрации.
- Тесты фиксируют критичные инварианты: допустимые диапазоны, типы команд, условия тревоги.

## Вопросы экспертов и ответы

**Почему симулятор, а не физические датчики?**  
Симулятор обеспечивает воспроизводимый сценарий и проверку логики без привязки к конкретному вендору. Доменный слой отделён от адаптера устройства; физический MQTT/HTTP адаптер — следующий интеграционный этап.

**Это уже готовая система видеонаблюдения?**  
Нет. В демо есть карточки камер и состояние канала, но реального видеопотока, записи и аналитики видео нет. Для этого нужен RTSP/WebRTC шлюз и отдельный сервис доступа к потокам.

**Что произойдёт без интернета?**  
Локальный стенд и его сценарии работают без внешнего облака. Удалённый доступ из интернета в этой версии не реализован.

**Как защищены команды?**  
На уровне домена проверяются идентификатор, online-статус, тип и допустимый диапазон. Для production понадобятся аутентификация, роли, TLS, rate limiting, аудит и тестирование угроз.

**Почему JSON, а не PostgreSQL?**  
Для локальной конкурсной сборки JSON убирает инфраструктурные зависимости и упрощает воспроизводимость. При многопользовательской нагрузке и интеграции с устройствами хранилище следует заменить на PostgreSQL/TimescaleDB с миграциями.

**Что бы вы сделали следующим?**  
Подключил бы один реальный датчик через MQTT, реализовал реальный адаптер и контрактные тесты, затем добавил управление пользователями и журнал аудита.
